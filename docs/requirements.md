# 家計簿Webアプリ 要件定義書 v1.1

作成日：2026-10-13
対象：Codexによる初期版（MVP）開発

## 1. 目的と前提

個人の収入・支出をスマートフォンやPCから手軽に記録し、月別・カテゴリ別に振り返れる家計簿Webアプリを開発する。

- 利用者は原則1人。本人のGoogleアカウントでのみアクセスできるようにする。
- Googleスプレッドシートを唯一の正本データ保存先とする。
- Google Apps Script（GAS）のWebアプリ機能で公開し、HTML/CSS/JavaScriptで画面を構築する。
- フロントエンドとGAS間の呼び出しには `google.script.run` を使用する。
- 日本円（JPY）の整数金額を扱う。日付・時刻の基準は `Asia/Tokyo` とする。
- UIはスマートフォン優先のレスポンシブデザインとする。
- 初期版で実装する：収支の登録、カテゴリ分類、取引履歴の閲覧・編集・削除、支払方法とカテゴリの設定、アプリ内の集計・グラフ。
- 初期版で実装しない：口座間振替、銀行・カードの自動連携、レシート読取、予算管理、複数ユーザー対応、実際の口座残高計算。

## 2. 画面と機能

### 2.1 入力画面（6項目）

1. **収支区分**：`支出` / `収入` の2択。初期値は `支出`。切り替え時にはカテゴリ候補を対応する区分に変更する。
2. **日付**：年・月・日を独立して選べるダイヤル式UIを基本とする。初期値は当日。過去日も選択可。存在しない日付は選択不可。端末差がある場合は操作しやすい代替UIを使用してよい。
3. **支払・入金方法**：選択式で、初期値は未選択。支出では「支払方法」、収入では「入金先」と表示してよい。同じ登録マスタを使用する。初期候補は `現金`、`クレジットカード（JALカード）`、`クレジットカード（JREカード）`、`Suica`、`ゆうちょ銀行`、`JREバンク`、`PayPay`。
4. **カテゴリ**：選択式の必須項目。収支区分に対応したカテゴリだけ表示する。初期値は未選択。設定画面で追加・名称変更・表示順変更・使用停止が可能。
5. **金額**：日本円の1円以上の整数のみ。スマホでは数字キーボードを表示し、入力値は3桁ごとのカンマ区切りで表示する。保存時はカンマを除去した正の整数とする。空欄、0、負数、小数、不正な文字列を拒否する。
6. **備考**：自由記述。空欄・改行を許容する。

**登録ボタンの動作**：必須項目が有効なときだけ押せる。送信中は多重送信を防ぐ。保存成功時のみ完了メッセージを表示し、収支区分を `支出`、日付を当日、支払方法・カテゴリを未選択、金額・備考を空欄に戻す。失敗または結果不明時は入力内容を維持する。再試行時に同一リクエストIDを再利用し、重複記録を防ぐ。

### 2.2 集計・グラフ画面（初期版で必須）

- 対象年月を選択できる。初期値は当月。
- **月間サマリー**：対象月の収入合計、支出合計、収支差額（収入－支出）を円で表示する。
- **カテゴリ別支出グラフ**：対象月の支出をカテゴリ別に集計し、円グラフまたはドーナツグラフで表示する。カテゴリ名、金額、構成比を確認できること。
- **月別推移グラフ**：選択月を含む直近12か月について、収入合計と支出合計を月ごとに比較できる棒グラフを表示する。
- データがない場合は `0円` や「データがありません」を適切に表示し、グラフ描画で例外を起こさない。
- 集計対象は `date`（取引日）で判定する。`created_at`（登録日時）ではない。
- 論理削除済みの取引を集計しない。編集後の内容を再集計に反映する。
- カテゴリの集計キーは `category_id` とし、名称変更で別カテゴリ扱いにならないようにする。
- ここで表示する「収支差額」は口座残高・資産残高ではないことを明示する。

### 2.3 履歴画面

- 登録済みの取引を日付の新しい順、同日なら登録日時の新しい順に表示する。
- 日付、収支区分、支払・入金方法、カテゴリ、金額、備考を確認できる。
- 対象年月、収支区分、カテゴリによる絞り込みを可能にする。
- 取引を選択して内容を編集できる。編集後は該当月の集計に反映する。
- 取引を削除する際は確認ダイアログを表示し、論理削除する。
- 一度に大量のデータを表示しないよう、1ページ50件程度のページ分割を行う。
- 行番号ではなく `transaction_id` で取引を特定する。

### 2.4 設定画面

**支払・入金方法**
- 追加、名称変更、表示順変更、使用停止、再有効化が可能。
- 初期候補は入力画面の項目3に記載した7種類。
- 使用停止したものは新規入力候補に出さず、過去の取引履歴は維持する。

**カテゴリ**
- `支出` と `収入` で独立したカテゴリ一覧を管理する。
- 追加、名称変更、表示順変更、使用停止、再有効化が可能。
- 同じ収支区分内で同名のカテゴリを重複作成できない。
- 初期カテゴリは以下とする（名称は設定画面から変更可能）。
  - 支出：`食費`、`日用品`、`交通費`、`住居費`、`光熱費`、`通信費`、`医療費`、`趣味・娯楽`、`教育費`、`交際費`、`その他`
  - 収入：`給与・アルバイト`、`仕送り`、`臨時収入`、`その他`
- 使用停止後も過去の取引や集計が失われないこと。

## 3. Googleスプレッドシートの構造

1つのスプレッドシート内に、以下3シートを作成する。初回起動時または専用セットアップ処理でヘッダーと初期マスタデータを作る。既存データを初期化処理で消してはいけない。

### 3.1 `Transactions`（取引）

| 列 | フィールド | 内容 |
|---|---|---|
| A | `transaction_id` | 一意のUUID |
| B | `date` | 取引日 `YYYY-MM-DD` |
| C | `type` | `income` または `expense` |
| D | `payment_method_id` | 支払・入金方法のID |
| E | `payment_method_name` | 登録時の名称（履歴表示の予備） |
| F | `amount` | 正の整数（JPY） |
| G | `note` | 備考 |
| H | `created_at` | 登録日時 |
| I | `updated_at` | 最終更新日時 |
| J | `deleted_at` | 論理削除日時。未削除は空欄 |
| K | `request_id` | 登録リクエストを一意に識別するID |
| L | `category_id` | カテゴリID |
| M | `category_name` | 登録時のカテゴリ名称（履歴表示の予備） |

既存のv1.0案にあったA～K列は維持し、カテゴリ関連の2列をL・Mに追加する。名称変更後も同じIDで集計し、表示名は原則としてマスタ上の現行名を利用する。マスタが参照不能な場合は取引行に保存した名称を使う。

### 3.2 `PaymentMethods`（支払・入金方法）

| フィールド | 内容 |
|---|---|
| `payment_method_id` | 一意のID |
| `name` | 名称 |
| `sort_order` | 表示順 |
| `is_active` | 使用中かどうか |
| `created_at` | 作成日時 |
| `updated_at` | 更新日時 |

### 3.3 `Categories`（カテゴリ）

| フィールド | 内容 |
|---|---|
| `category_id` | 一意のID |
| `type` | `income` / `expense` |
| `name` | カテゴリ名 |
| `sort_order` | 表示順 |
| `is_active` | 使用中かどうか |
| `created_at` | 作成日時 |
| `updated_at` | 更新日時 |

## 4. データ処理の原則

- 金額はシート上でも数値（整数）として保存し、収支区分で方向を表す。負数で支出を表現しない。
- 日付は文字列 `YYYY-MM-DD` に正規化する。日時はタイムゾーンを明確に扱い、端末やシートのタイムゾーン差で日付が前後しないようにする。
- サーバー側でも、必須項目・金額・日付・カテゴリと収支区分の整合性・支払方法とカテゴリの有効性を検証する。
- 新規登録処理では `LockService` 等を用いて同時書き込みを制御し、`request_id` が既存なら二重登録しない。
- 編集時は `transaction_id` を維持して `updated_at` のみ更新する。削除時は `deleted_at` を設定し、他の情報を残す。
- カテゴリまたは支払方法が使用停止されても、過去の取引は保持する。過去の取引を編集するときは既存の使用停止項目を確認・表示できるよう配慮する。
- 備考や名称は、スプレッドシートに書き込む際の数式解釈とHTML表示時のスクリプト実行を防ぐ。
- 集計は取引レコードから導出し、集計値を正本データとして二重管理しない。

## 5. 認証・公開・設定

- Google Apps ScriptのWebアプリは本人限定アクセスを基本とする。
- スプレッドシートの共有設定を確認し、第三者がデータを閲覧・編集できないようにする。
- スプレッドシートIDなどの設定はサーバー側の設定値（例：Script Properties）で管理し、画面や公開コードに秘密情報を埋め込まない。
- デプロイ方式、必要権限、初回認可、スプレッドシート準備、更新手順をREADMEに記載する。
- 認証・アクセス制限の実環境での確認が必要な場合は、ユーザー向けの検証手順を提示する。

## 6. 受け入れテスト

1. 新規支出：`2026-10-13`、`現金`、`食費`、`680円`、備考 `昼食` を登録でき、`Transactions` に正しい値が1行保存される。
2. 新規収入：`収入` に変更すると収入カテゴリだけが表示され、収入が正しく保存される。
3. 未入力の支払方法・カテゴリ・金額、0円・負数・小数・不正な日付は登録できない。
4. 閏年の2月29日を正しく扱い、存在しない日付は選べない。
5. 登録ボタンの連続操作や通信結果不明時の同一リクエスト再送で、重複行が作られない。
6. 登録直後の入力フォームの初期化と、保存失敗時の入力保持が仕様どおり動作する。
7. 支払方法とカテゴリを追加・名称変更・使用停止でき、使用停止後も過去の履歴を読める。
8. 履歴の編集・削除後、一覧と集計に変更が反映される。
9. 月間サマリーの収入合計・支出合計・収支差額が手計算と一致する。
10. カテゴリ別グラフの金額と比率が明細の合計と一致する。
11. 直近12か月の月別収入・支出グラフが、年をまたいでも正しく表示される。
12. 取引のない月でもエラーにならない。
13. スマートフォンとPCのブラウザで入力・閲覧ができる。
14. 第三者にアプリとシートが公開されていないことをアクセス設定と実機で確認できる。

## 7. 将来拡張：口座間振替

初期版では**実装しない**。ただし、以下の原則を保持する。

- 「ゆうちょ銀行から現金に1万円移動」のような振替は、収入でも支出でもない。
- 将来の振替機能は、移動元・移動先・金額・日付を管理する独立した取引種別またはデータ構造として設計する。
- 振替金額を収入合計や支出合計に加えない。
- 現段階の `PaymentMethods` は選択肢管理用であり、口座残高そのものを管理するマスタではない。
- 将来変更する場合は既存取引を失わない移行処理を用意する。

## 8. Codexへの実装指示

1. この仕様を正本として、最初に構成図・ファイル一覧・実装順・想定リスクを簡潔に提示する。
2. Google Apps ScriptのHTML Serviceを使用し、複雑な外部基盤を不要とする構成を優先する。
3. 登録・一覧・編集・削除・設定・集計の順に段階的に実装する。各段階で動作確認を行う。
4. 初期化処理は冪等にし、再実行しても既存取引・設定を消さない。
5. 処理失敗を握りつぶさず、利用者に分かるエラーメッセージを表示する。
6. 完成時に、ソースコード、`README.md`、初期セットアップ手順、デプロイ手順、テスト項目と結果を提供する。
7. Googleアカウントへの認可や公開設定など、ユーザーの実操作が必要な工程は、その旨を明記する。
8. テストを実行できなかった箇所を明示し、未確認事項を「検証済み」とは記載しない。
9. 仕様にない機能を勝手に大規模追加せず、判断が必要なときは既定の仮定を説明する。
